# auto-sales worker（フォーム営業の実行役）

OS本体（Next.js）とは別プロセス。DBの `auto_sales_jobs` を見張って、
QUEUED のジョブを Playwright で1件ずつ処理する。

**このワーカーを Railway に常駐させることで、拠点側はブラウザだけで完結する。**
以前ローカルPCで回していたのはこのプロセス。別PCが必要だったのはそれが理由。

## Railway への登録手順

同じ Railway プロジェクト内に**2つ目のサービス**として追加する。
（1つ目＝Next.js本体。ルートの `railway.json` はそちらが使う）

1. Railway プロジェクト → **New** → **GitHub Repo** → `hirokishirakawa-collab/adarch-estimate`
2. 作られたサービスの **Settings**:
   - **Root Directory**: `/`（空欄のまま。Dockerfile がリポジトリ直下から `worker/` と `prisma/` を COPY するため、サブディレクトリに絞ってはいけない）
   - **Config-as-code path**: `worker/railway.json`
   - **Networking**: ドメインを割り当てない（HTTPサーバを持たないため）
3. **Variables** に下記を設定
4. Deploy

## 環境変数

| 変数 | 必須 | 既定値 | 説明 |
|---|---|---|---|
| `DATABASE_URL` | ○ | — | 本体と同じ Railway PostgreSQL。`${{Postgres.DATABASE_URL}}` で参照する |
| `ANTHROPIC_API_KEY` | ○ | — | サイト解析・フォーム解析（Claude Haiku） |
| `CONCURRENCY` | | `5` | 並列レーン数。DB接続数は `CONCURRENCY + 1` で自動追従 |
| `DAILY_LIMIT` | | `3500` | グループ全体の1日の送信上限。拠点ごとの上限は本部が承認画面で設定する |
| `SEND_WINDOW_START` | | `8` | 送信を始める時刻（時） |
| `SEND_WINDOW_END` | | `20` | 送信を止める時刻（時）。`0`と`24`で24時間稼働 |
| `SUBMIT_DELAY_MS_MIN` | | `15000` | 1レーンあたりの送信間隔（下限） |
| `SUBMIT_DELAY_MS_MAX` | | `30000` | 1レーンあたりの送信間隔（上限） |
| `POLL_INTERVAL_MS` | | `10000` | キューが空のときの待機時間 |
| `DRY_RUN` | | `false` | `true` で送信ボタンを押さない。**初回稼働は必ず true で確認する** |
| `HEADLESS` | | `true` | `false` でブラウザを表示（ローカル調査用） |
| `AUTO_SALES_REPLY_EMAIL` | | `media@adarch.co.jp` | フォームに入れる返信先。反響トラッキングはこの受信箱を見る |
| `RESIDENTIAL_PROXY_URL` | | — | 未設定でも動く。reCAPTCHA対策が必要になったら設定 |
| `TWOCAPTCHA_API_KEY` | | — | CAPTCHA突破サービス。未設定なら CAPTCHA サイトはスキップして手動に回る |

## スループットの目安

1件あたりの実処理は20〜50秒（平均35秒前後）。これに送信間隔15〜30秒（平均22秒）が乗るので、
**1レーンの1サイクルは約57秒**。

| レーン数 | 8:00-20:00（12時間） | 24時間稼働 |
|---|---|---|
| 3 | 約2,270件/日 | 約4,550件/日 |
| **5** | **約3,790件/日** | 約7,570件/日 |
| 8 | 約6,060件/日 | 約12,100件/日 |

既定の `CONCURRENCY=5` × 送信時間帯8:00-20:00 で、**1日3,000件は余裕を持って収まる**
（`DAILY_LIMIT=3500` が先に効いて止まる）。

レーンを増やすときはメモリを見ること。Playwright のページは1枚あたり150〜250MB使う。
Railway 2GB プランなら5が上限の目安。8以上にするなら4GBプランへ。

### 送信時間帯

既定は 8:00〜20:00。深夜に問い合わせフォームが届くと機械送信だと分かりやすいので、
日中に寄せている。24時間回すなら `SEND_WINDOW_START=0` / `SEND_WINDOW_END=24`。

## 上限は2段構え

| 段 | どこで決める | 効き方 |
|---|---|---|
| グループ全体 | ワーカーの `DAILY_LIMIT` | 全拠点の合計。ここに達すると全部止まる |
| 1アカウント | 本部が承認画面で設定（`dailyLimit`） | そのアカウントだけ止まる。他拠点は動き続ける |

**アカウント単位の上限は既定200件/日で、無制限にはできない。** 上限は1〜1000件/日。
1社が突出して送りすぎるとグループ全体の毀損になるため、構造として必ず上限を持たせている。
承認後も同じ画面から変更できる。カウントは実際に送信した件数（COMPLETED）で、
失敗やスキップは消費しない。毎日0:00にリセット。

## 返信先アドレス

フォームのメール欄には、テンプレートに登録された**その拠点の @adarch.co.jp アドレス**が入る。
テンプレート作成時に必須で、@adarch.co.jp 以外は登録できない。
**未設定のテンプレートはワーカーが送信を拒否する**（本部の media@ に返信が集まって
拠点が反響に気づけなくなるため）。承認もできない。

反響トラッキング（`api/auto-sales/check-replies`）は、実際に送信に使われたアドレスを
ジョブから逆引きして、その受信箱を1つずつ見に行く。サービスアカウントはドメイン全体の委任を
持っているので、@adarch.co.jp の任意のユーザーに成り代わって読める。
1つの受信箱で失敗しても、残りの受信箱の処理は続行する。

## 二重送信の防止（全社共通）

`auto_sales_sent_domains` が全社共有の送信済み台帳。`domain` に UNIQUE が張ってあり、
これが二重送信ガードそのものになっている。判定キーは URL ではなく**正規化ドメイン**
（`www.` を落として小文字化、パス・クエリ・ポートを除去）。
拠点Aが `/contact`、拠点Bが `/inquiry` に登録していても同じ会社と判定する。

チェックは3段階:

1. **営業先の登録時** — 他拠点が送信済みならエラーで登録させない（CSV取込はスキップ＋理由を返す）
2. **送信の直前** — 登録後に他拠点が送っている可能性があるので再確認。該当すれば SKIPPED
3. **送信の成功時** — 台帳へ INSERT。UNIQUE 違反なら他拠点が先に載せたということなので握りつぶす

正規化のロジックは `src/lib/auto-sales-domain.ts` と `worker/src/domain.ts` に同じ実装がある。
**片方だけ直すとガードがすり抜ける。必ず両方直すこと。**
マイグレーションのバックフィルSQLも同じ結果を出す必要がある（12ケースで突合せ済み）。

全社の送付履歴は OS の `/dashboard/auto-sales/history` で全拠点が閲覧できる。
送信した本文とスクリーンショットは自拠点分のみ（モニター画面）。

## 安全側の作り

- **本部が承認したテンプレートのジョブしか処理しない**（`isApproved: true`）。
  承認取消をすると、キューに残っているジョブも自動的に止まる。
- ページ内に「営業お断り」等の文言を見つけたら送信せず、そのドメインを
  `auto_sales_blacklist` に自動登録する（全拠点に共通で効く）。
- ブラックリスト登録済みドメインはスキップする。
- 同じドメインへ複数レーンが同時にアクセスしないようにしている。
- 同一ジョブの二重送信は `status=QUEUED` を条件にした更新で防いでいる。

## ローカルで動かす

```bash
cd worker
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm ci
ln -sfn ../../src/generated src/generated   # Dockerfile と同じ配置にする
npx playwright install chromium
DRY_RUN=true CONCURRENCY=1 npx tsx src/index.ts
```
